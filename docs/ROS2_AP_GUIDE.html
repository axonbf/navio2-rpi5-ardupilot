ArduPilot native-DDS (/ap) reference

Reference for driving this boat (ArduRover on Navio2 + Pi 5) from ROS 2 over the native XRCE-DDS bridge. Setup/rationale: see docs/ROS2_HUMBLE_DDS_PLAN.md and config/ros2-dds/.

Connect

Everything is Fast-DDS on ROS_DOMAIN_ID=0 (the agent decides this). The AP-specific types need ardupilot_msgs built (see the DDS plan doc / install notes).

# On the Pi:            source ~/ros2_env.sh      &&  source ~/ap_ws/install/setup.bash
# Laptop @ home (LAN):  works with the default env (+ source ~/ap_ws/install/setup.bash)
# Laptop remote (wg):   source ~/ros2_boat.sh     &&  source ~/ap_ws/install/setup.bash
ros2 topic list ; ros2 service list

Actions

AP_DDS currently exposes topics + services only — no ROS 2 actions. Goal-style behaviour is done via the /ap/goal_lla / /ap/cmd_gps_pose topics.

Parameters

Two ways: the ROS 2 param services above (get/set_parameters, by name), or QGC (full list). The DDS transport itself is configured by these ArduPilot params:

ParamValueMeaning
DDS_ENABLE1Enable AP_DDS
SERIAL5_PROTOCOL45DDS-XRCE on serial5 (→ /dev/ttyDDS0)
SERIAL5_BAUD115115200 (nominal on a PTY)
DDS_DOMAIN_ID0ROS domain (must match your env)
DDS_UDP_PORT, DDS_IP*—UDP transport (NOT used — dead on Navio2/Linux; see plan doc)

Common recipes

# Read GPS / state
ros2 topic echo /ap/navsat
ros2 topic echo /ap/status          # needs ardupilot_msgs

# Drive it (GUIDED)
ros2 service call /ap/mode_switch ardupilot_msgs/srv/ModeSwitch "{mode: 15}"
ros2 service call /ap/arm_motors  ardupilot_msgs/srv/ArmMotors  "{arm: true}"
ros2 topic pub /ap/cmd_vel geometry_msgs/msg/TwistStamped \
    "{twist: {linear: {x: 0.5}, angular: {z: 0.2}}}" -r 10
ros2 service call /ap/arm_motors  ardupilot_msgs/srv/ArmMotors  "{arm: false}"

# Params
ros2 service call /ap/get_parameters rcl_interfaces/srv/GetParameters "{names: ['CRUISE_SPEED']}"
⚠️ Armability — what /ap can and can't tell you. /ap/prearm_check returns only a generic success: true/false + "Vehicle is Not Armable". /ap/status gives the armed flag / mode. The detailed reason (e.g. "PreArm: GPS: waiting for 3D fix") is NOT exposed over /ap — it's a MAVLink STATUSTEXT, so read it in QGC (or over the MAVLink link). Armable becomes true when the enabled ARMING_CHECK items pass (GPS lock, RC not in failsafe, EKF healthy, battery OK …).
Safety. Arming makes the boat live. On the bench with the ESC/motors powered, arm + a mode can spin the props. Keep it disarmed / props clear until you mean it.
/ap/joy — RC override (command any channel, any mode). /ap/joy is ArduPilot's input (it subscribes), not telemetry — it overrides up to 8 RC channels at the RC-input layer, the same mechanism as MAVLink RC_CHANNELS_OVERRIDE.
  • axes[i] range −1.0 to +1.0 → linearly mapped to channel i's RCx_MIN–RCx_MAX PWM. Requires axes_size >= 4.
  • axes[i] = NaN → releases channel i back to the physical RC.
  • Auto-release after 1 s of no /ap/joy messages → you must publish continuously to hold an override.
  • Works in any mode (MANUAL, ACRO, STEERING, GUIDED…), so it's the direct "drive the boat from ROS 2" path — for a skid-steer boat publish throttle (ch3) + yaw (ch4). There is no raw /ap/servo topic — /ap/joy is the closest thing to per-motor control.
ros2 topic pub /ap/joy sensor_msgs/msg/Joy "{axes: [0.0, 0.0, 0.0, 0.0]}" -r 10   # neutral, hold
# Skid-steer: axes[2]=throttle (-1 rev .. +1 fwd), axes[3]=yaw (-1 right .. +1 left)
ros2 topic pub /ap/joy sensor_msgs/msg/Joy "{axes: [0.0, 0.0, 0.5, 0.0]}" -r 10   # half fwd
